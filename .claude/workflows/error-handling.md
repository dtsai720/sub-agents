# 品質控制與錯誤處理

## Sub-agent 結果驗證清單

- ✅ 交付文件是否存在且可讀取
- ✅ 文件格式是否符合規範
- ✅ 內容完整性是否達標
- ✅ 技術決策是否合理
- ✅ 是否有明顯的疏漏或錯誤

## 處理策略

### 1. 品質不足時
- 重新調度同一 Sub-agent
- 在 prompt 中加入具體改進要求
- 提供前次輸出作為參考
- 明確指出需要改進的項目

### 2. 發現依賴問題時
- 調度前置 Sub-agent 補充缺失資訊
- 更新工作流程，避免後續再次發生

### 3. 技術方案有疑慮時
- 調度架構師 Agent 進行審查
- 提供具體的疑慮點供分析
- 基於審查結果決定是否調整方案

### 4. 跨 Agent 不一致時
- 識別不一致的根源
- 調度相關 Agent 進行對齊
- 必要時調度架構師 Agent 仲裁

## 錯誤處理情境

### 情境 1：Task tool 調用失敗

**錯誤碼：** AGENT_EXEC_FAIL

**原因：** Sub-agent 執行超時或錯誤

**處理步驟：**
1. 記錄錯誤資訊（Agent 名稱、任務描述、錯誤訊息）
2. 檢查是否因 prompt 過長或格式錯誤
3. 若可修復：調整 prompt 後重試（最多 2 次）
4. 若無法修復：向用戶說明問題，詢問是否調整需求

---

### 情境 2：Sub-agent 回報品質不足

**錯誤碼：** QUALITY_CHECK_FAIL

**原因：** 交付物缺失、格式錯誤、內容不完整

**處理步驟：**
1. 分析具體缺失項目（缺少哪些必要內容？）
2. 組合改進要求（明確指出需要補充的內容）
3. 重新調用同一 Sub-agent（最多 3 次）
4. 若 3 次後仍未達標：拆分任務或降低要求

---

### 情境 3：用戶中途改變需求

**錯誤碼：** REQUIREMENT_CHANGED

**處理步驟：**
1. 評估影響範圍（哪些已完成的階段需要重做？）
2. 識別需要重做的 Sub-agent（產品經理？架構師？開發？）
3. 向用戶說明影響（時間成本、已完成的工作）
4. 確認後重新調度相關 Sub-agent

---

### 情境 4：發現技術衝突

**錯誤碼：** TECHNICAL_CONFLICT

**原因：** 前後端 API 不匹配、資料庫設計衝突、技術選型矛盾

**處理步驟：**
1. 識別衝突點（具體是哪些技術決策衝突？）
2. 調用架構師 Agent 仲裁（提供雙方的技術方案）
3. 更新相關文件（DESIGN.md、OPENAPI.yaml）
4. 重新調度受影響的 Sub-agent（使用更新後的設計）

---

### 情境 5：缺少必要 Sub-agent 定義

**錯誤碼：** AGENT_NOT_FOUND

**原因：** .claude/agents/ 目錄缺少對應的 .md 檔案

**處理步驟：**
1. 檢查是否有替代 Agent（例如：缺少後端開發-Go，但有後端開發-Python）
2. 若有替代：詢問用戶是否使用替代 Agent
3. 若無替代：提示用戶建立對應的 Agent 定義檔案
4. 提供範本協助用戶快速建立

---

## 迭代改進機制

- 最多允許 3 次迭代改進
- 若 3 次後仍未達標，應重新評估需求或拆分任務
- 每次迭代都要提供明確的改進方向

## Sub-agent 輸出格式要求

每個 Sub-agent 必須在單次執行中完成任務，並以以下格式輸出：

```
## 📋 任務完成報告
**Agent 身分：** [Agent 名稱]

**完成任務：**
[具體完成的工作內容，包含關鍵決策和實作細節]

**交付文件：**
- 文件 1：{檔案路徑或內容摘要}
- 文件 2：{檔案路徑或內容摘要}

**品質自檢：**
✅ 已完成項目：
- [項目 1]
- [項目 2]

⚠️ 需注意事項：
- [注意事項 1]（若無則寫「無」）

**技術決策：**
- [重要的技術選型、架構決策、或設計考量]

**建議下一步：**
- 推薦 Agent：[Agent 名稱]
- 原因：[為什麼需要這個 Agent]
- 所需輸入：[需要哪些文件或資訊]
```

⚠️ **重要提醒：**
- Sub-agent 無法等待或進行多輪互動
- 必須在單次回應中完成所有工作
- 若任務過於複雜，應拆分為多個獨立的 Sub-agent 任務
